### 范围

- 在修改代码前创建 `task-workspaces/T002/plan.md`；审查过程中维护 `implementation.md`；完成后创建 `verification-and-handoff.md`。
- 验证默认开发环境与叠加 usage 配置均可解析并按文档运行。
- 验证 `/api/health` 的环境/数据库识别、两库隔离、迁移一致性、开发样例数据幂等性和使用库无自动样例数据。

- 通过真实浏览器验证桌面主流程、搜索、详情侧栏、表单和控制台状态。
- 审查代码是否符合现有规则、模块边界、PostgreSQL 唯一事实源和 T001 验收标准。

### 非范围

- 不新增产品功能，不实现 AI Gateway、任务队列、面经、embedding、RAG 或移动端专属能力。
- 不把 390px 等移动视口作为正式验收项；只记录明显的小屏崩坏，不做专项适配。
- 不调用 ImageGen。
- 本任务默认不修改业务实现。发现缺陷时记录证据、影响和建议；需要修复时由总管另行派发任务。
- 不执行项目规则禁止的 `npm run build`。

### 可自主决策项

- 选择与风险相称的测试命令、浏览器路径、API 样例和代码审查顺序。
- 选择临时测试数据，但必须可识别并在验证结束后安全清理，不能污染 usage 数据库。
- 根据仓库 Git 状态选择可用审查基线；若无可靠固定点，明确记录限制并对当前 T001 实现范围执行标准/规格双轴审查。

### 验收标准

1. `plan.md`、`implementation.md`、`verification-and-handoff.md` 均按规范完成。
2. 开发/usage 两套 Compose 配置、健康检查和数据隔离得到独立证据；测试数据不会留在 usage 库。
3. 核心 API 和桌面 UI 主流程均得到可复现的通过/失败记录，浏览器控制台状态明确。
4. 审查结果按严重性列出问题，并明确区分代码标准问题、规格不符、文档不一致和未覆盖风险。
5. 给出清晰阶段门结论：通过、带条件通过或不通过；不得在存在未解决阻断问题时标记 T002 完成。

### 验证要求

- 执行并记录与 Python、Compose、迁移、API、数据库隔离和浏览器流程相称的验证；不要求使用固定命令，但每项必须有结果。
- UI 按项目规则人工验证，可使用浏览器测试工具辅助，不新增访问脚本。
- 若环境权限或外部依赖阻塞，记录复现步骤、已尝试项和最小解除方式。

### 文档更新要求

- 只更新 T002 工作区、T002 任务状态和与审查结论直接相关的实施状态；不得把未修复问题写成已完成。
- 不直接重写产品边界；发现与确认决策冲突时在交接中标注并停止相关扩展。
- 普通审查结论不写入技术架构；只有已经验证的架构事实或重要取舍才按 `docs/tech-architecture/AGENTS.md` 增量更新。

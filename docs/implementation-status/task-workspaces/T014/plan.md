# T014 任务计划：规则优先的准备评估与任务建议业务链路

## 目标与成功标准

在目标岗位、结构化面试情报和知识/算法/项目/实习四条独立轨道之上，提供 `daily | weekly | pre_interview` 三种显式请求模式。相同数据库事实、相同请求参数和相同评估日期必须得到相同优先级档位、排序和解释；每条建议必须携带轨道、目标、稳定标识、reason codes、来源分类、业务 ID 和证据状态/引用。

## 实现假设

- 评估即时只读生成，不新增持久化评分、计划、定时任务或 Worker job。
- API 请求显式携带 `mode`、`as_of_date` 和可选目标画像；`pre_interview` 可额外携带明确的 `application_id + interview_date`。
- 现有 `applications.key_date` 未区分面试日期类型，不足以单独证明临近面试；只有调用方明确给出面试日期、投递处于 `interview` 且日期在有界窗口内时才启用弱信号。
- 情报频率只作为需求 reason，不表示用户能力；不读取全量面经正文，只读取规范题、occurrence 聚合和最多三条证据片段。
- 不统一四轨道数据模型。知识/算法状态、项目/实习确认事实、待核实草稿和表达版本按各自语义生成或降级建议。

## 实施步骤与逻辑检查

1. 建立独立 planning 请求/响应契约与只读聚合服务；逻辑检查显式触发和无写入副作用。
2. 为四轨道生成候选建议，按固定 priority tier、mode rank、弱信号和稳定 ID 排序；逻辑检查同快照复现性和 tie-break。
3. 只在可信临近面试上下文中启用有界弱信号；逻辑检查 stage/key_date 不会单独放大优先级。
4. 返回安全证据引用、来源分类、业务 ID、限制与降级说明；逻辑检查事实/草稿/表达/情报互不污染。
5. 增量更新唯一稳定技术实现文档和索引，完成 T014 实施、逻辑检查与交接记录。

## 范围边界

只修改 T014 后端业务/API 注册、任务工作区和 `docs/tech-architecture/implementation/` 稳定文档。不实现页面、导出、semantic recall、embedding/pgvector、RAG、LLM、Agent、调度/推送、全量正文读取、统一评分或四轨道改模。

## 验证边界

遵循用户最高优先级规则，不编写或执行 pytest、单元/集成/E2E、迁移验证、API/数据库运行态验证、页面/浏览器验收、测试脚本、静态语法检查或 `npm run build`。编码后只做数据/状态边界、排序复现性、tie-break、事实分类、投递弱信号上限、证据回链、主动触发、无全量正文输入和非范围的逻辑检查。Git scoped diff、敏感信息和工作树检查只用于提交范围控制。

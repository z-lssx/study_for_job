# 决策记录

本文档记录 grill 中已经确认的产品边界、MVP 范围和后续延期项，避免散落在对话里，也避免和产品文档、技术文档重复打架。

## 1. 当前定位

- 单用户
- 本地优先
- Web 应用
- PostgreSQL 为唯一业务事实源
- 面经模块是“情报层”
- 其余模块是“准备轨道”
- 以用户自主准备为主，系统引导为辅

## 2. 面经模块

面经不是普通内容页，而是全局情报输入。

- 负责采集、清洗、去重、抽取、归一化
- 保留原文、证据片段、题目出现记录和高频统计
- 支持手动补充链接或正文
- 支持用户手动触发分析
- 支持自动处理额度，但不做面向用户的定时任务；面经抓取、分析和聚合由页面或 API 主动触发，Worker 只可为失败任务做延迟重试
- 自动额度指“允许自动推送和处理的面经数量”
- 手动额外推送不占自动额度，但仍记录 token 消耗
- 手动推送时可以给面经链接，要求系统爬取并分析
- 处理失败时保留失败原因，允许后续补正文或重新触发
- 面经内容要先标注再拆分：原文 -> 轮次 -> 内容块 -> 检索 chunk
- 内容块包括问题、原作者答案、反馈、追问、过程描述
- 原作者答案要保留，但不直接等同于标准答案
- 高频统计必须来自原始证据，不允许被后续用户编辑污染
- 用户可编辑 AI 提炼结果，但编辑只影响个人复习层

## 3. 八股模块

八股不是百科式知识库，而是把外部知识和面经高频题转成“可口述、可追问、可复习”的内容。

- 支持题目入口和知识点入口
- 支持随机抽题练习
- 支持知识点关联，但不做复杂评分图谱
- 知识点关联可以自动生成，但要支持用户编辑和合并
- 不做虚假的单值打分
- 可记录轻量掌握状态，如理解程度、能否口述、是否答过追问、最近复习时间
- 不追求沉淀百科式完整标准答案
- 更重视外部高质量资料链接、面试可口述版本、高频追问和踩坑点
- AI 生成的八股内容支持用户编辑，并保留原始版本

## 4. 算法模块

算法模块不做在线编辑、运行和判题，只负责组织练习和复盘。

- 通过外部平台链接承接刷题动作
- 记录题目状态、卡点、复盘、掌握度
- 可接收面经情报的弱影响，用于题型权重调整
- 面经中常见算法题型可以单独放一个小板块
- 题型权重受面经频率、目标方向相关性、掌握度、最近练习时间影响
- 已经掌握很多的题型要降权

## 5. 项目 / 实习模块

项目和实习以“经历证据包”为核心，简历文字由证据包派生。

- 主要保存经历证据和表达版本
- AI 负责整理、总结、补缺口
- 用户可编辑 AI 生成内容
- 不允许 AI 覆盖用户修订版
- 证据包包含 30 秒版、2 分钟版、背景目标、个人职责、团队边界、架构技术选择、困难和取舍、可核实指标、岗位考点映射、追问树
- 不允许事实编造

## 6. 投递记录模块

投递记录只是手动维护的求职流程看板，不是知识输入主源。

- 记录公司、岗位、方向、投递渠道、当前阶段、关键日期、下一步动作、备注或链接
- 不做岗位爬取
- 不做首页重点展示
- 默认不参与准备评估智能体的核心输入
- 仅在临近面试时作为很弱的信号，用来缩窄准备范围

## 7. AI 与智能体边界

- 云端大模型指内置 agent 调用的远程 LLM
- 用户主动上传内容可以送云端处理
- 自动爬取内容可以按任务进入云端处理，但要有额度限制和开关
- 只对少量关键场景开放动态 prompt
- 动态 prompt 不做零散变量拼接式的全量配置
- 智能体模块定位为“准备评估与策略生成”，不是通用聊天框
- 智能体输入只取各模块摘要和 Top-K 证据，不喂全量正文
- 智能体结果必须带来源，不允许只给结论不留证据
- token 统计要按模块拆分，面经分析要单独展示
- token 面板重点看自动批处理和手动分析的消耗

## 8. MVP 范围

MVP 只做能把主链路跑通的内容。

- 面经采集、抽取、去重、分析
- 八股题目与知识点管理
- 算法题单与掌握度记录
- 项目 / 实习证据整理
- 投递看板
- 手动触发的准备评估报告；报告可以包含每日、每周和面试前的任务建议，但系统不会自动按时间生成或推送
- 随机抽题练习（轻量单题功能，与后续多轮模拟面试分开）
- 管理端（仅关键 prompt/参数配置和 token 统计）
- Markdown 和 JSON 导出

## 9. MVP 明确不做

以下内容先不进 MVP。

- 登录 / 多用户体系
- 发布回滚
- 面向用户的定时任务
- 在线判题
- LeetCode 账号同步
- 自动化岗位爬取
- 完整公司差异化画像
- 更细的知识图谱可视化
- 更强的自动评分
- 重型运维能力
- 通用聊天型智能体

## 10. 后续再做的内容

- LeetCode 账号同步
- 面经定时任务
- 更复杂的公司差异化画像
- 更细的知识图谱可视化
- 更强的自动评分
- 多用户体系
- 自动化岗位爬取
- 更完整的备份与恢复
- 更复杂的智能体自动化编排
- 多轮模拟面试：串联面经、八股、算法、项目和实习数据的后续 Agent 流程

## 11. 不再继续 grill 的判断

当前核心边界已经明确：

- 每个模块的职责已经分清
- MVP 和后续版本已经分层
- AI 输入边界已经收窄
- 投递记录已经回到看板定位
- 数据导出与本地优先策略已经确认

因此，后续不需要继续围绕产品边界反复 grill。接下来应该进入数据库设计、表结构拆分和 API 设计。

## 12. 本次 grill 保留下来的关键约束

- 面经是情报层，不是普通内容页
- 八股是把外部知识和高频题转成可答能力
- 算法只做外部平台的练习组织，不做判题
- 项目和实习要做证据化，不做事实编造
- 投递记录是看板，不是知识输入主源
- 智能体是准备评估器，不是万能聊天框
- 动态 prompt 只对关键场景开放
- token 与额度都要有可视化统计
- 数据可以导出，避免本地优先导致锁死

## 13. AI 开发协作方式（2026-08-01，2026-08-02重构）

- 使用三层协作：项目大总管维护宏观阶段与跨阶段依赖；阶段总管负责一个阶段内的规划和开发任务派发；开发 Agent 只负责一个边界明确、可独立验证的结果。
- 整个项目只有一个项目大总管逻辑身份，同一时间最多一个活跃大总管对话。用户负责首次启动以及必要时的明确替换；替换对话恢复同一逻辑身份，不形成“第一代/下一任”等多代权威。
- 大总管状态、当前宏观阶段、唯一活跃阶段总管及其 ID、最近验收证据和下一项允许动作统一记录在 `docs/implementation-status/program-status.md`。新的或恢复后的大总管对话必须先检查该控制状态，无法排除双重权威时停止派发。
- 项目大总管同一时间只管理一个活跃阶段总管。阶段总管由大总管创建，完成后把交接返回同一个大总管，不自行创建下一阶段总管或项目大总管。
- 大总管上下文影响准确性时进入“暂停”并写入恢复检查点；用户可以恢复原对话或明确替换对话。MVP/项目完成时直接标记“项目完成”，不会触发新的大总管。
- 大总管与阶段总管均不承担代码开发，不读取源码或 diff，只消费对应层级的结构化摘要和状态文档。
- 项目大总管与阶段总管可直接维护、提交和推送自己负责的治理文档；纯文档提交不再转派开发 Agent，但提交范围不得混入业务代码或未说明改动。
- 阶段交接前必须整理本阶段文档：把稳定事实提炼到唯一事实源、消除相邻任务重复、归档被替代的过程材料并修复索引，避免长期文档膨胀。
- 项目大总管维护 `program-status.md`、`roadmap.md` 和项目级治理；阶段总管维护 `current.md`、`queue.md`、阶段计划与交接；开发 Agent 维护任务工作区和技术实现事实，避免多层文档重复保存同一状态。
- 项目规则使用分层 `AGENTS.md` 管理：根文件只保留全局规则，前端、后端和特殊领域在对应目录维护局部规则。
- 项目大模型服务确定使用 DeepSeek V4；具体模型档位、embedding 供应方式和调用参数由后续实现按需要决定。
- MVP 当前只要求本地运行，同时保持模型、存储和部署边界可替换，避免阻碍未来扩展。
- 面经来源的抓取许可仍需按来源确认。实现时只尝试公开、无需登录的内容，并始终保留用户手动提交正文的降级入口。
- 关键技术决策、非显而易见的实现机制和经过验证的工程取舍需要增量沉淀到 `docs/tech-architecture/`，供维护、复盘和面试表达使用。

## 14. 客户端支持范围（2026-08-02）

- 产品主要用于个人桌面场景，桌面 Web 是唯一正式支持端。
- 保留当前基础响应式，只要求小屏不严重崩坏；不再把 390px 等移动视口作为每个任务的正式验收项。
- MVP 及当前后续计划不开发移动端专属导航、手势、底部栏、PWA、离线同步或原生客户端。
- 如果未来确有手机快速查看的高频需求，再单独评估极简只读页。

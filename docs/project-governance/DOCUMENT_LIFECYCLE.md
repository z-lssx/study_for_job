# 阶段文档整理与归档规则

本规则用于控制长期 AI 开发中的文档膨胀、事实重复和交接噪音。阶段总管在阶段交接前负责执行，大总管在阶段验收时检查结果。

## 目标

- 一个事实尽量只有一个稳定事实源，其他文档使用链接和简短引用。
- 保留必要的验证证据和技术取舍，同时降低相邻任务重复描述造成的上下文噪音。
- 让下一阶段优先读取少量索引、当前状态、稳定实现文档和阶段交接，而不是遍历所有任务过程材料。

## 稳定事实源

- 产品边界与用户价值：`docs/product-overview/`。
- 已确认产品/协作决策：`docs/decision-log/`。
- 系统级设计和已验证机制：`docs/tech-architecture/overview.md`、`decisions/`、`implementation/`。
- 面试表达材料：`docs/tech-architecture/interview/`，它是引用工程事实的派生层，不作为 Agent 判断实现状态的事实源。
- 宏观阶段与当前进度：`docs/implementation-status/program-status.md`、`roadmap.md`、`current.md`、`queue.md`。
- 阶段计划与交接：`management-plans/`、`handoffs/`。
- 单任务过程证据：`tasks/` 与 `task-workspaces/`，完成后不再作为跨阶段首选入口。

## 阶段交接前的整理步骤

1. 盘点本阶段新增或修改的文档，按“稳定事实、当前状态、过程材料、已失效内容”分类。
2. 将跨任务重复但仍有效的实现事实提炼到对应的技术实现/决策文档；将跨阶段状态提炼到 `program-status.md` 或 `current.md`。
3. 为重复事实选择唯一事实源。其他文档删除重复段落或缩减为一句结论加链接，不在多个交接、任务记录和当前状态中复制大段内容。
4. 检查相邻任务文档的重叠：阶段交接只总结组合后的阶段能力、验证结论和剩余风险，不重复粘贴每个任务的完整命令和实现细节。
5. 将已经被稳定文档替代、且只具有过程追溯价值的材料移动到 `docs/implementation-status/archive/<阶段标识>/`；维护归档索引，记录原路径、归档原因和替代事实源。
6. 更新所有 README/索引和引用路径，检查不存在断链、重复入口或把计划写成成果的问题。
7. 生成最终阶段交接，明确下一任真正必读的少量文档；详细过程材料放入“按需追溯”，不列为全部必读。
8. 阶段总管自行检查 scoped 文档 diff，提交并推送文档收口；记录 SHA 和工作树状态。

## 归档规则

- 优先归档而不是删除，尤其是仍包含唯一验证证据、失败复现或历史决策背景的材料。
- 可归档：已完成任务的冗长过程计划、已被阶段总结替代的临时状态、过期的管理草案、重复的验证副本。
- 不归档为不可见：当前有效产品决策、当前架构、关键技术决策、已验证实现机制、当前路线图/状态/队列、最近阶段交接。
- 归档目录必须有 README，说明内容、原路径和当前替代入口。
- 只有确认没有唯一信息、没有外部引用且没有审计价值时才可删除文档；不确定时保留归档。
- 不为追求文件数量少而把所有信息重新堆入一个大文件；按职责维持索引化、小而稳定的事实源。

## 去重判断

以下内容通常只保留一个详细版本：

- 同一批验证命令与结果
- 同一数据模型或状态机说明
- 同一风险与限制
- 同一任务完成清单
- 同一提交 SHA 与推送结果

任务交接保留任务级证据，技术实现文档保留稳定机制，阶段交接保留组合能力和跨阶段影响，宏观状态只保留阶段级结论。四者职责不同，不互相复制全文。

## 禁止事项

- 不得在整理时改写用户未确认的产品决定。
- 不得把未验证计划合并成已实现事实。
- 不得为了去重删除唯一的测试证据、失败原因或迁移风险。
- 不得通过全量暂存提交混入业务代码或其他任务改动。

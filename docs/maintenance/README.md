# 增量维护与补丁开发

项目 MVP 已实现，后续默认采用单任务、直接补丁式开发，不再恢复“大总管 → 阶段总管 → 开发 Agent”的阶段管理链路。

## 开发入口

每个补丁只解决一个边界明确的问题。开始前按需阅读：

1. 根目录 `AGENTS.md` 与 `README.md`；
2. `docs/product-overview/README.md`；
3. `docs/decision-log/README.md` 中与补丁直接相关的产品边界；
4. `docs/tech-architecture/README.md`、`overview.md` 和对应模块实现文档；
5. 视觉或交互修改额外阅读 `docs/design/frontend-redesign.md`；
6. `known-issues.md` 中与修改范围相关的遗留风险。

不要求普通补丁读取历史阶段计划、任务交接、旧队列或历史开发对话。

## 补丁规则

- 一个对话负责一个可独立说明和提交的补丁；需要并行时只使用同一对话内的子 Agent，不建立项目管理层级。
- 先明确问题、影响范围和成功条件，再修改代码；存在会改变产品边界的歧义时询问用户。
- 精准修改，不顺手重构无关模块，不为一次性问题新增抽象层或未来配置。
- 优先复用现有领域接口和 PostgreSQL 事实，不复制数据，不建立第二事实源。
- 前端视觉与交互修改继续遵循 `frontend-design` 和现有桌面工作台设计规范。
- 按根目录最高优先级规则，编码完成后只做逻辑检查，不新增或执行测试、构建、lint、类型检查、迁移/API/数据库运行态或浏览器验证，除非用户在具体补丁中明确改变该要求。
- 未执行项必须如实记录，不得宣称运行通过。

## 文档维护

- 行为、数据语义、可靠性、安全边界或重要演进条件发生变化时，直接更新对应 `docs/tech-architecture/implementation/` 文档。
- 新的长期产品决定写入 `docs/decision-log/README.md`；普通实现选择不进入产品决策。
- 新增全局架构取舍时在 `docs/tech-architecture/decisions/` 建立独立决策记录。
- 临时计划、聊天摘要、逐步操作日志和重复验证记录不提交到长期文档。
- 已知但本次不修复的问题统一维护在 `known-issues.md`，修复后删除或更新对应条目。

## Git 边界

- 提交只包含当前补丁和必要文档更新，显式检查未混入密钥、运行产物或其他任务改动。
- 删除的历史治理和阶段文档仍保存在 Git 历史中，可使用 `git show <commit>:<path>` 查看，或使用 `git restore --source=<commit> -- <path>` 恢复。
- 当前 GitHub `origin` 的归属尚未在本环境验证。向该远端推送会发送本地项目代码，必须获得用户针对具体远端的明确授权；不得绕过安全限制。

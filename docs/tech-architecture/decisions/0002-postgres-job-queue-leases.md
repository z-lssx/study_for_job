# 0002：PostgreSQL 任务队列采用短事务领取、租约与至少一次执行语义

状态：已确认并实现
日期：2026-08-02

## 背景与问题

阶段一需要把页面/API 主动创建的长任务交给独立进程执行，并支持并发领取、失败退避和 Worker 崩溃恢复。PostgreSQL 已是唯一事实源，MVP 不希望为本地单用户场景引入 Redis、Celery、RabbitMQ 或独立 Scheduler。

## 最终选择

- 使用 `jobs` 保存当前任务事实，`job_attempts` 保存每次租约与执行结果。
- Worker 在短事务内以 `FOR UPDATE SKIP LOCKED` 选择到期任务、关闭过期 attempt、生成 lease token 并创建新 attempt；提交后才运行处理器。
- 运行期间通过独立短事务续租；成功/失败写回必须匹配任务 ID、`running` 状态与 lease token。
- 执行语义明确为至少一次。租约恢复允许任务重新执行，未来有外部副作用的业务处理器必须使用业务幂等键或等价约束。
- 可重试错误采用有界指数退避，永久错误或达到最大尝试进入终态；`next_run_at` 不开放为用户定时参数。

## 考虑过的替代方案

- Redis/Celery 或其他消息中间件：成熟但增加第二事实源、部署和故障面，不符合当前本地 MVP。
- API 内后台线程：进程重启会丢失状态，长任务占用 API 生命周期，不能独立扩缩。
- 长事务持有行锁直到处理完成：实现直观但外部 I/O 会扩大锁等待、连接占用和崩溃恢复复杂度。
- 精确一次执行：数据库无法原子撤销任意外部副作用；以 lease token 声称精确一次会产生错误安全感。

## 理由与代价

该方案复用现有 PostgreSQL、迁移和连接管理，用少量表与明确状态机提供可查询、可恢复的执行事实。代价是轮询存在小延迟，过期租约可能导致重复处理；所有后续业务处理器必须按至少一次语义设计。

## 影响与验证

- 两个真实 PostgreSQL 并发领取者针对单任务只产生一个租约；领取事务完成后不保留外部执行期间的行锁。
- 租约过期会关闭旧 attempt 并创建新 attempt；旧 token 的迟到成功写回被拒绝。
- 数据库级部分唯一索引验证重复幂等键返回同一任务，参数漂移被拒绝。
- 开发与 usage 数据库均应用 `003_job_queue.sql`；usage 保持 0 任务、0 attempt。

## 后续演进条件

只有在部署规模、吞吐或跨系统投递需求证明 PostgreSQL 轮询成为瓶颈时，才评估消息中间件。T005 起每个处理器需声明幂等边界、外部副作用与可重试错误分类。

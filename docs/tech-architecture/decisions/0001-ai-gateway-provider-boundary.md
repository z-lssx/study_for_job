# 0001：AI Gateway 使用自有契约与本地确定性 provider

状态：已确认并实现  
日期：2026-08-02

## 背景与问题

项目已确认云端大模型方向为 DeepSeek V4，但阶段一没有真实凭据，也不能让业务代码、prompt 管理或可追溯日志被单一供应商 SDK 锁定。外部权限缺失还不能阻塞本地产品闭环。

## 最终选择

- 业务模块只依赖自有 `AiGateway` 和 `AiProvider` 协议。
- DeepSeek 作为 OpenAI-compatible provider 适配，默认使用 SophNet base URL；model 由环境提供，key 采用 `DEEPSEEK_API_KEY` 显式覆盖、`SOPHNET_API_KEY` 本地兜底。
- 默认 provider 是明确标识的确定性 fake，实现相同契约并支持受限失败模拟；它只用于本地链路验证，不冒充真实模型结果。
- Gateway 统一负责 prompt 校验/渲染/hash、trace、token 结构和成功/失败日志，供应商适配器只负责远程协议与错误映射。

## 考虑过的替代方案

- 业务代码直接使用 OpenAI/DeepSeek SDK：接入短，但供应商响应、异常与配置会渗入各业务模块，日志难以保持唯一实现。
- 等待真实凭据后再开发：会把外部权限变成产品阻塞，无法确定性覆盖失败和 token 日志。
- 在数据库中管理 provider/key：超出单用户 MVP，扩大密钥泄露与错误配置面。

## 理由与代价

该方案用很小的协议层换取可替换性、统一可追溯性和无凭据验证。代价是维护一层自有契约，并且 fake 只能证明本地数据流，不能证明 DeepSeek 的真实模型标识、token 口径或错误体。

## 影响与验证

- 切换 fake/DeepSeek 不修改业务调用方；密钥不进入数据库、日志、API 或前端。
- 7 个契约测试覆盖成功、失败、超时、缺配置、未知异常与 compatible 响应解析。
- 开发库真实写入 3 成功/3 失败日志并按模块/场景聚合 168 token；使用库保持 0 调用日志。

## 后续演进条件

只有在真实业务需要流式响应、多模态、工具调用或多个非兼容供应商时扩展协议；确认 DeepSeek V4 模型标识后补一次固定诊断，不改变当前业务边界。

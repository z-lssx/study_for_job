# 技术架构文档规则

本目录同时服务工程协作和用户面试准备，但两类文档必须分层，不能互相替代。

## Agent 工程事实层

- `overview.md`：仍然有效的系统级架构地图。
- `decisions/`：有实际影响的技术取舍、替代方案、关键不变量和演进条件。
- `implementation/`：已经实现并验证的数据流、精确机制、默认参数、约束和验证证据。

这些文档是开发 Agent 理解上下文的技术事实源。只有会影响数据一致性、并发、失败恢复、性能、安全、成本、可观测性、外部依赖或后续实现的决定才值得记录；普通 CRUD、样式调整和机械重构不记录。

重要工程决定应按需要记录：解决的问题、最终选择、关键不变量、会改变行为的精确默认参数/公式、替代方案、代价、验证证据和演进触发条件。只写已实现并验证的事实，不复制大段代码，不为了面试效果夸大设计。

## 用户面试材料层

- `interview/`：面向用户的项目讲解、常见追问、回答结构、量化证据和局限说明。

面试材料是从工程事实层提炼的派生内容，不是实现事实源。每篇材料必须链接对应的 `decisions/`、`implementation/` 或验证文档；若表述冲突，以工程事实层为准。普通开发 Agent 默认不需要读取 `interview/`，只有任务明确涉及简历、复盘或面试准备时才读取和更新。

面试材料可以为了表达重复少量关键结论，但不得复制整篇架构文档，也不得把计划、建议或未来演进写成当前成果。

## 维护顺序

1. 开发任务先把已实现事实写入 `decisions/` 或 `implementation/`。
2. 验证完成后，只有具备明确面试价值的技术亮点才同步提炼到 `interview/`。
3. 工程实现变化时先更新事实层，再检查受影响的面试材料，避免派生内容陈旧。

# PostgreSQL 任务队列与 Worker：面试准备

> 本文是面试表达材料，不是实现事实源。事实依据：[技术决策 0002](../decisions/0002-postgres-job-queue-leases.md)、[Worker 实现记录](../implementation/job-queue-worker.md)、[T004 验证交接](../../implementation-status/task-workspaces/T004/verification-and-handoff.md)。

## 30 秒回答

项目是本地单用户 MVP，PostgreSQL 已经是唯一事实源，所以我没有立即引入 Redis/Celery，而是用 `jobs` 保存任务当前状态、`job_attempts` 保存每次执行历史。Worker 通过短事务 `FOR UPDATE SKIP LOCKED` 领取任务，事务外执行；lease token、心跳和过期恢复提供至少一次执行，业务侧再用幂等键控制重复副作用。可重试失败使用默认 5 秒起步、300 秒封顶的有界指数退避。这个设计降低了本地部署复杂度，但承认轮询延迟和重复执行风险，规模增长后再评估 jitter 或消息中间件。

## 为什么不用 Celery、Redis 或 RabbitMQ

当前约束：

- 本地单用户，任务量和吞吐有限。
- PostgreSQL 已是业务和任务事实源。
- 目标是先获得可查询、可恢复的后台执行能力，不增加第二套服务和故障面。

因此复用 PostgreSQL 的收益大于引入消息中间件。代价是 Worker 采用轮询，存在最多约一个轮询周期的领取延迟；如果未来吞吐、跨系统投递或数据库负载成为可测瓶颈，再迁移到消息系统。

## 为什么拆成 `jobs` 和 `job_attempts`

- `jobs` 表示任务当前事实，适合列表、调度和状态查询。
- `job_attempts` 表示每次领取/执行事实，保留成功、失败、重试计划和租约过期历史。

如果只用 `jobs`，每次重试会覆盖历史，难以解释任务为什么失败或恢复；如果只保存事件，查询当前可执行任务会更复杂。拆表是在当前状态查询与审计追溯之间做的平衡。

## 如何避免多个 Worker 同时领取

Worker 在短事务中按优先级、到期时间和创建时间选择任务，并使用 `FOR UPDATE SKIP LOCKED`：

- 行锁保证同一领取周期只有一个 Worker 更新该任务。
- `SKIP LOCKED` 让其他 Worker 跳过已被领取的行，不相互阻塞。
- 事务提交后才执行处理器，外部 I/O 期间不长期持有数据库锁。

这只能避免同一租约周期的重复领取，不能承诺业务副作用精确一次。

## Worker 崩溃后如何恢复

- 每次领取生成新的 lease token 和租约到期时间。
- 处理期间心跳用独立短事务续租。
- Worker 崩溃后租约停止续期，后续 Worker 可以关闭旧 attempt 并创建新租约。
- 成功或失败写回必须匹配 `job_id + running + lease_token`，因此旧 Worker 即使迟到也不能覆盖新租约结果。

系统明确采用至少一次语义：租约恢复可能让处理器再次执行，而数据库 token 无法撤销已经发生的 HTTP 调用或其他外部副作用。

## 有界指数退避怎么计算

设当前已经执行的 attempt 编号为 `n`，基础间隔为 `B`，最大间隔为 `M`：

```text
delay_seconds(n) = min(M, B × 2 ^ max(0, n - 1))
next_run_at = failure_time + delay_seconds(n)
```

当前默认 `B=5` 秒、`M=300` 秒，所以在最大尝试次数足够时序列为：

```text
5, 10, 20, 40, 80, 160, 300, 300 ...
```

第一次失败从 5 秒开始，因为 `n=1`。当前没有 jitter：本地低并发任务没有明显的同步重试风暴，确定性延迟更容易测试和复现。如果未来出现多 Worker、大量同源失败或远程 API 限流，再考虑 full jitter 或 decorrelated jitter。

指数增长避免持续故障时高频重试，300 秒上限避免等待无限增长。只有错误可重试且仍有尝试余量时才写 `next_run_at`；永久错误或耗尽尝试直接终止。

## 幂等是怎么做的

创建层使用 `(job_type, idempotency_key)` 部分唯一索引：

- 同一键且参数相同，返回已有任务。
- 同一键但参数漂移，返回 409，避免悄悄复用错误任务。

这只解决任务创建去重。未来面经抓取等具有外部副作用的处理器，还必须使用规范化 URL、内容哈希或等价业务唯一键保证处理器幂等。

## 索引设计如何解释

- 部分唯一索引覆盖具有幂等键的任务，数据库成为去重事实源。
- 活跃任务部分复合索引只覆盖 `queued/retry_wait/running` 等调度相关状态，并匹配优先级、到期时间和创建顺序的领取谓词。
- 列表和 attempt 查询使用与排序匹配的索引，避免用一个宽索引承担所有访问模式。

面试时应强调“索引围绕查询谓词设计”，不要只背索引名称。精确 DDL 以迁移为准。

## 验证证据

- 21 项常规测试和 4 项真实 PostgreSQL 集成测试通过。
- 两个并发领取者针对同一任务只获得一个租约。
- 租约恢复后旧 token 的迟到写回被拒绝。
- 退避单元测试在 `B=5`、`M=12` 时得到 `5, 10, 12`。
- 真实 PostgreSQL 生命周期验证失败后的精确 `next_run_at`、最大尝试终止和幂等参数漂移拒绝。

## 主动说明的局限

- 这是至少一次，不是精确一次。
- 默认 1 秒轮询、60 秒租约，没有吞吐自适应。
- 当前没有 jitter、取消、进度、DAG 或归档。
- 尚未做吞吐压测和数据库故障注入。

这些限制符合当前本地 MVP，并且都有明确演进触发条件，不应包装成已经解决的大规模分布式问题。
